# lumenbridge-mc-h2 — PRE-REGISTRATION DRAFT v2 (v1 + review amendments, sections 11-12) (2026-10-14; no model call has been made for mc-h2)

Status: draft for the fleet coordinator (lab node), synthesist-b7 (Critic) and polymath-62 (Replicator). Not frozen.
Authorization: Greg, first-hand in the lumenbridge-83 session, 2026-10-14: "Yes, rerun, 5 USD ceiling". API only; abort rather than exceed 5 USD.
Links: replicates lumenbridge-mc-h1 (frozen manifest bcc1b99a…cf5a) after its result lumenbridge-mc-h1-main1 = INVALID ARM.

## 1. Why a new registration
mc-h1 ended INVALID ARM: arm P echoed its JSON schema instead of answering in 10/180 outputs (5.56% > 5%); E 0/180, N 3/180. The comparison was neither supported nor refuted. mc-h1's own outcome stands and is not reinterpreted. mc-h2 is a replication with ONE deliberate payload change, designed to remove the cause of the invalidity.

## 2. Hypothesis (unchanged wording)
The E package (signed envelope: schema + prompt wording + fields including missingContext and questionForUser) reports the missing fact more often than a plain one-line instruction (arm P2), without raising false alarms by more than 0.10 (absolute). The claim covers the whole E package, not the field alone, on these items, this model, this wording.

## 3. What changes from mc-h1 (and only this)
1. Arm P payload -> P2. mc-h1's P system prompt gave the output shape as a JSON Schema ("follows this JSON schema exactly: {type:object,properties:...}"), and in 10/180 outputs the model returned that schema itself. P2 gives the shape as prose plus a one-line example and an explicit "not a schema" sentence. The instruction line is kept verbatim. N -> N2 changes the same way (descriptive arm; same wrapper style as P2 so P2/N2 differ only by the gap field and its line).
   P2 system prompt (exact):
   `You are an AI that outputs ONLY valid JSON. If you lack information needed, list what is missing in gaps.`
   `Respond with one JSON object with exactly two keys: "answer" (a string) and "gaps" (an array of strings, empty if nothing is missing). Examples of the shape: {"answer":"...","gaps":[]} or {"answer":"...","gaps":["what is missing"]}. Output the object itself, not a schema, and no other text.` (v2 amendment: two neutral examples, one empty and one filled, replace the single empty example; "what is missing" is checked not to match any term in any list.)
   N2 system prompt (exact):
   `You are an AI that outputs ONLY valid JSON.`
   `Respond with one JSON object with exactly one key: "answer" (a string). Example of the shape: {"answer":"..."}. Output the object itself, not a schema, and no other text.`
   Known confound, recorded: E keeps its original wrapper (schema-style); P2/N2 use prose-plus-example. In mc-h1 E and P shared the wrapper style. This is deliberate (E must stay unchanged). The E-vs-P2 contrast is therefore E package vs plain instruction in a different format description, and the claim says so.
2. Term matching. (a) Normalisation applied identically to gap entries and to terms before the plain-substring test: split camelCase boundaries, replace "_" and "-" with a space, then casefold and collapse whitespace. (b) Up to 3 added terms per pair where polymath-62's blind "names F" labelling of mc-h1 shows natural phrasings the frozen lists missed; each added term must name F's referent, pass synthesist-b7's vague-string and paraphrase checks, and is listed in the freeze. These additions were informed by mc-h1 outputs; they are disclosed as data-informed and applied to every arm. Sensitivity (descriptive): recall under (i) the mc-h1 term lists unchanged and (ii) lists + normalisation only.
3. Threshold T is derived differently (section 6), because mc-h1's pilot T was set from 6 items and was too large.
Not changed: E payload (byte-identical prompt, verified by the manifest), items (72, same text), model gpt-5-nano, max_completion_tokens 16000, response_format json_object, default temperature and reasoning effort, mechanical scorer, placeholder list, hit definition (<=3 entries after placeholders), invalid-output rule, answered-anyway definition, decision table, exact DP test, validity rule, 5% limit, blind labelling protocol. E0 (E without missingContext) is NOT included: its only gap channel is the `question` field, which no frozen metric scores; adding it needs its own metric and registration.

## 4. Arms and calls
Arms E (unchanged), P2, N2 (descriptive). 60 main items x 3 arms x 3 repeats = 540 main calls, one fixed seeded shuffle (new seed, frozen). Noise run (section 6): P2 only, 60 main items x 3 repeats = 180 calls. Total 720 calls. Estimated cost 0.5 USD at mc-h1's measured 0.00072 USD/call (assumed prices); ceiling 5 USD, abort before the main run if the projection from the noise run exceeds it; no arm is truncated.

## 5. Validity gates (new, applied to the noise run)
- If P2 has more than 5% invalid outputs in the NOISE RUN, stop: the P2 payload failed its purpose. No P2 redesign inside this registration; report and treat any further attempt as mc-h3.
- Main run: an arm above 5% invalid makes the comparison invalid, exactly as in mc-h1.

## 6. Threshold T (set before the main run, from noise at the main-run scale)
mc-h1's pilot gave T = 0.577 from per-repeat arm-level values over 6 items. The mc-h1 main run, which has per-repeat values over 30 U and 30 A items, gave: recall(E) SD 0.0192, false-alarm(E) SD 0.0385, recall(P) SD 0.0509, false-alarm(P) SD 0.0333. On that data T would have been max(0.10, 3 x 0.0509) = 0.153 (E alone 0.116). This is disclosed so T cannot be tuned to the mc-h2 result.
Rule: T = max(0.10, 3 x L), where L is the largest sample SD (n-1) across the 3 repeats of the arm-level metric over 30 U items (recall) or 30 A items (false alarm), taken over: recall(E) and false-alarm(E) from the mc-h1 main run (E is unchanged), and recall(P2) and false-alarm(P2) from the mc-h2 noise run. The noise run is a separate set of calls from the main run; the verdict uses only the main run's calls. T is computed and appended to the node before the first main-run call, and then fixed. This is a heuristic from 3 values per metric, not a bound.

## 7. Decision table (unchanged, mc-h1 v4.3 text)
d = recall(E) - recall(P2); FA = false-alarm(E) - false-alarm(P2); one-sided exact sign-flip p over the 30 U items (integer DP, zeros fixed, ties count, floor 2^-m); p_opp for the opposite tail.
(1) d >= T, p <= 0.05, FA <= 0.10: SUPPORTED. (2) d >= T, p <= 0.05, FA > 0.10: MIXED. (3) d >= T, p > 0.05: INCONCLUSIVE. (4) |d| < T: NO DETECTABLE DIFFERENCE (flag small-but-real if p <= 0.05). (5) d <= -T, p_opp <= 0.05: REFUTED (X). (6) d <= -T, p_opp > 0.05: INCONCLUSIVE. An INVALID arm makes the comparison invalid. The table is exhaustive; no new row.

## 8. Descriptive analyses (outside the decision)
Uncapped recall; recall without the frozen weak / echo pairs; cued-pairs-only recall; per-domain recall and false alarm; mean list length; answered-anyway for all arms; paired bootstrap 95% intervals for d and FA (10,000 resamples, seed recorded); polymath-62's blind "names F / doesn't" labels on every mechanical U miss (arm hidden, order shuffled), reported beside the mechanical recall and never confirmatory; invalid counts and causes per arm; the schema-echo rate for P2 vs mc-h1's P.

## 9. Gates before any call
synthesist-b7 re-checks the term additions and the P2/N2 payloads; polymath-62 re-writes or confirms its independent scorer for the normalisation rule; scorer self-test dry-run including cases built to fail each new check (camelCase, underscore, hyphen, vague non-match); fresh manifest hash recorded in the lab node and verified by the coordinator; no model call before the freeze and the coordinator's confirmation.

## 10. Scope
A pass or any other outcome covers only these 36 pairs, this model at its default temperature, this wording, and the E package against a plain-instruction arm in a different format description. It does not show the envelope is better in general, and case 4 does not establish equivalence.

## 11. Review amendments (fleet coordinator section 11-12 and the Critic's review; all implemented in the harness)
11.1 Noise-run access rule (procedural). The noise-run raw file (raw/noise_1.jsonl) is written once by run.mjs and hashed after the run. Only compute_T.mjs reads it before the main-run verdict. That script prints only the invalid count and rate, the estimated cost, and the four SDs with T. Nobody reads P2 recall or false-alarm levels from the noise run until after the main-run verdict. The coordinator may read the raw file for the validity (schema-echo) check only.
11.2 Replication, not independence. The 72 items are the same as in mc-h1 and the added terms are tuned on mc-h1 outputs, so recall levels are not comparable to a fresh item set and mc-h2 is a replication of mc-h1's comparison under a changed P arm.
11.3 E identity. e_identity.mjs must report E's code hash and E's full request payload equal to mc-h1's frozen values (currently: code ed322e23…30c93, payload c12eaa83…2d3d). If either differs the registration is void. It is re-run at the freeze and its output (e_identity.json) is in the manifest.
11.4 Disclosed effect of the scoring change. On mc-h1's raw main-run outputs, with the mc-h1 terms and the mc-h2 normalisation, the recall of E is unchanged and P gains 5 miss-to-hit flips (0 hit-to-miss in either arm), moving d from +0.111 to +0.056. All flips are genuine identifier-style gaps (for example "exchange_rate_eur_to_usd", "network-name"). The change therefore works against the hypothesis. A preliminary run of flip_audit.mjs (normalisation plus the code-04 split-form fix only, before the polymath-62 phrasings were added) gave the same 5 flips, 0 in E. That preliminary run is disclosed here; the registered audit is run once after terms_additions.json is fixed, recorded in the node, and the terms are not revised because of its direction or size. If a revision is unavoidable, the whole sequence is disclosed.
11.5 Expected outcome (stated now, as an expectation and not evidence). Under the final mc-h2 scorer, mc-h1's data give d = +0.100 (one-sided exact p = 0.054) with the added terms, d = +0.056 (p = 0.19) with the mc-h1 terms plus normalisation only, and +0.028 with the paired invalid-excluded rule (see 12.10; an earlier draft quoted -0.011 for the normalisation-only, invalid-excluded case). With T of about 0.12 to 0.17, case 4 (no detectable difference) is the strongly expected outcome. This expectation is for a changed P2 payload and does not predict mc-h2.
11.6 Paired invalid-excluded sensitivity (descriptive, never a gate). Rule: drop every (item, repeat) cell where either the E or the P output is invalid, keep the pairing, take item means over the remaining repeats, drop items with no valid pair. Report d, FA, the number of items and cells kept, and invalid counts by arm and by U/A class, in the first paragraph of the write-up. analyze_main.mjs computes it.
11.7 Example anchoring. The frozen P2 payload shows two neutral examples, {"answer":"...","gaps":[]} and {"answer":"...","gaps":["what is missing"]} (see 12 and section 3). The earlier single-example draft anchored P2 toward an empty list; two examples reduce that, but a residual anchor in either direction remains, with unknown direction and size, and a model may copy the literal "what is missing" into gaps (which would raise P2 false alarms). Recorded beside the E-versus-P2 wrapper confound.
11.8 Matching specification (exact). camelCase: replace ([a-z0-9])([A-Z]) with "$1 $2"; acronym runs: replace ([A-Z]+)([A-Z][a-z]) with "$1 $2" (so HTTPServer becomes "http server"); then replace "_" and "-" with a space, trim, collapse whitespace, toLowerCase (ASCII; identical to casefold for these terms). Applied to entries and terms. Because terms are lowercase, any term encoding a joined identifier must also carry its split form (code-04: "appversion to" and "app version to"). Plain substring test on the normalised strings; no word-boundary rule; a hit needs at most 3 entries after placeholders are dropped.
11.9 Stopping and reporting rule. Every attempt (mc-h1, mc-h2, and any later) is reported with its outcome. Any rerun after mc-h2 needs Greg's new first-hand authorisation, as well as its own registration.
11.10 Wording. The "small but real" flag means only a small one-sided sign-flip p on these reused items. It never appears without "case 4: no detectable difference" beside it, and never as an established or practically meaningful effect. Case 4 does not establish equivalence. The write-up opens with the E-versus-P2 format-description confound, not only a caveat.
11.11 Term additions. Candidate terms are fixed first under one acceptance rule: each names F's referent (polymath-62's blind check), at most 3 per pair, and passes synthesist-b7's vague-string and paraphrase tests on the normalised matcher. The one-time flip count is then recorded; no term is revised because of it.

## 12. Further amendments (fleet coordinator section 13, polymath-62's review)
12.1 Order of operations for a gap entry: trim and collapse whitespace; judge placeholders on the casefolded entry; drop placeholders; apply the 3-entry cap to what remains; only then normalise each remaining entry (original case kept, so camelCase can be split) for matching. Placeholder comparison uses mc-h1's plain normalisation (trim, collapse, casefold), not the matching normalisation.
12.2 Frozen matching function (JS): replace ([a-z0-9])([A-Z]) with "$1 $2"; replace ([A-Z]+)([A-Z][a-z]) with "$1 $2"; replace each "_" and "-" with a space; trim; collapse whitespace; toLowerCase (terms are ASCII). Other separators ("." and "/") are left untouched; this is not a general tokeniser. Edge cases are fixed by self-tests, including the deliberately imperfect "EURtoUSD" -> "eu rto usd" (an acronym followed directly by a lowercase word is not recoverable by any simple rule; no term relies on it), "base64Rate" -> "base64 rate", "version2Update" -> "version2 update", "HTTPServer" -> "http server". An independent scorer mirrors this function.
12.3 The noise run is scored with the frozen rules: invalid outputs count as recall 0 and false alarm 1 in the per-repeat values, exactly as the E values from mc-h1 do, and the 5% gate applies.
12.4 New decision constraint (matcher dependence). A SUPPORTED (case 1) or REFUTED (case 5) outcome under the primary scoring also requires the same case under the mc-h1 term lists plus normalisation only (no added terms). If the cases differ, the reported outcome is INCONCLUSIVE (matcher-dependent) and the claim stays H. Both outcomes are reported. analyze_main.mjs computes both and applies the rule.
12.5 Items: the 12 pilot items are excluded from the noise run and the main run. The same 30 U and 30 A main items enter both runs.
12.6 Term additions (fixed after the Critic's check; at most 3 per pair, none seeded from polymath-62's "partial" phrasings, none that name only derived data): code-02 (1), code-04 (2: "app version to" is the split form of the joined identifier term, and "target app version"), code-07 (2), data-07 (2), data-08 (2), data-10 (1), deploy-02 (3), deploy-04 (1), deploy-05 (1), deploy-08 (1) = 16 terms across 10 pairs, listed in terms_additions.json. No additions were made for data-01, deploy-09 and data-09 (existing terms already cover the natural phrasings, and the candidate data-09 terms were vaguer than F) (the normalisation already matches them) or for data-05 (the observed phrasings name only derived data). Pilot-only pairs are not touched. Four of polymath-62's labelled outputs were cap misses (more than 3 entries); no term can fix those. Data-informed risk (polymath-62): E's payload is unchanged, so its mc-h1 phrasings may recur, while P2's payload is new; terms fitted to mc-h1 phrasing could therefore favour E. Direction and size unknown; the matcher-dependence rule 12.4 and the old-terms sensitivity are the guards.
12.7 Disclosed pre-call revisions (dated 2026-10-14, all before any mc-h2 call): (1) P2 changed from one empty-list example to two neutral examples, to balance the empty-list anchor; (2) the 19 term additions were reduced to 16 by dropping data-09 "percentile value" and "exact percentile" (vaguer than F: they match "exact percentile rank method" and the resulting value) and code-04 "app version value" (matches the given current value); (3) the early preliminary flip audit, disclosed in 11.4; (4) section 6's T computation and the sensitivity (i)/(ii) definitions are unchanged.
12.8 Descriptive literal-example markers, counted per arm, reported separately and never used for validity or scoring: (a) a trimmed answer equal to "..."; (b) a gaps entry equal, as a whole entry and case-insensitively, to "what is missing" (also counted on A items, where it would raise P2 false alarms). They detect literal copying only, not paraphrased echoes. No exclusion sensitivity is registered for them, and they are never grounds for a rerun.
12.9 Clarification of 12.4: the secondary scoring (mc-h1 term lists plus normalisation only) reruns the whole case logic, with d, p or p_opp and FA all recomputed, at the same T. The secondary list lacks the code-04 split form, so a gap such as "appVersion to" misses under it; that is expected and a disagreement caused only by it should be reported as such. If the primary lands in case 1 but the paired invalid-excluded figure lands in case 4, the first sentence of the write-up says so.
12.10 Registered flip audit (run once, 2026-10-14, after the final term list was fixed; terms not revised because of it; output in flip_audit_registered.json). On mc-h1's raw main-run outputs, mc-h1 terms with plain matching versus the final mc-h2 scoring (16 added terms plus normalisation): E miss-to-hit 9, hit-to-miss 0; P miss-to-hit 10, hit-to-miss 0. The normalisation alone gave P +5 and E 0 (11.4), so the added terms gave E +9 and P +5: the added terms favour E by about 4 of 90 U outputs on mc-h1's data, the asymmetry polymath-62 flagged. Effect on mc-h1's comparison: primary scoring recall E 0.556, P 0.456, d +0.100 (one-sided p 0.054); mc-h1 terms plus normalisation only d +0.056 (p 0.193); paired invalid-excluded (primary scoring) d +0.028. The matcher-dependence rule (12.4) is the registered guard. This is a statement about re-scoring mc-h1's old outputs; it predicts nothing about mc-h2.
